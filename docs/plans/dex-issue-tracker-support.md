# Plan: dex Issue Tracker Support

## Goal

Add dex as a first-class issue tracker option in Matt Pocock's upstream-style skills setup, without reintroducing the old `task-backend` abstraction.

After this change, a user running `/setup-matt-pocock-skills` can choose **dex**, and the setup skill writes `docs/agents/issue-tracker.md` with enough concrete `dex` CLI guidance for these skills to work:

- `to-prd`
- `to-issues`
- `triage`

## Branch

Use a dedicated branch for implementation and testing:

```bash
git switch -c add-dex-issue-tracker-support
```

## Design constraints

- Follow the current upstream abstraction: issue tracker behavior is configured through `docs/agents/issue-tracker.md`, not through a code adapter.
- Do not bring back `.skills/config.toml`, `task-backend`, or backend resolver scripts.
- Treat dex tasks as the issue tracker primitive.
- Use dex parent tasks for PRD-to-implementation fan-out.
- Use dex blockers for issue dependencies.
- Be explicit that dex does not have GitHub-style labels or comments.
- Store triage metadata in the task description.
- Keep the change small enough to be upstreamable.

## Implementation steps

### 1. Add the dex issue tracker template

Create `skills/engineering/setup-matt-pocock-skills/issue-tracker-dex.md`.

The template should say that issues and PRDs live as dex tasks and that all operations use the `dex` CLI.

Document these operations.

#### Create an issue

```bash
dex create "$TITLE" --description "$BODY"
```

#### Create a PRD

Create a top-level dex task. Put the PRD body in the description and include metadata identifying it as a PRD:

```markdown
Issue-Kind: prd
Triage-State: needs-triage
Triage-Type: enhancement
```

Then create it:

```bash
dex create "$TITLE" --description "$BODY"
```

#### Create child implementation issues

Use dex parent tasks for PRD-to-implementation breakdowns:

```bash
dex create "$TITLE" --description "$BODY" --parent "$PARENT_ID"
```

#### Represent blockers

Use dex's native blocker support:

```bash
dex create "$TITLE" --description "$BODY" --blocked-by "$BLOCKER_IDS"
dex edit "$ID" --add-blocker "$BLOCKER_IDS"
dex edit "$ID" --remove-blocker "$BLOCKER_IDS"
```

`$BLOCKER_IDS` is comma-separated.

#### Read an issue

Use full output for human-readable work and JSON for precise parsing:

```bash
dex show "$ID" --full
dex show "$ID" --json
```

#### List issues

```bash
dex list
dex list --json
dex list --all --json
dex list --query "needs-triage" --json
```

`dex list` only shows pending tasks by default. Use `--all` if completed tasks matter.

#### Apply triage roles

dex does not have labels. Store triage roles as metadata at the top of the task description:

```markdown
Issue-Kind: issue | prd
Triage-Type: bug | enhancement
Triage-State: needs-triage | needs-info | ready-for-agent | ready-for-human | wontfix
```

When changing triage state:

1. Read the full task.

   ```bash
   dex show "$ID" --full
   ```

2. Edit the description text, preserving the rest of the body.
3. Replace the description.

   ```bash
   dex edit "$ID" --description "$UPDATED_DESCRIPTION"
   ```

#### Add comments or triage notes

dex has no comment stream. Append AI triage notes and agent briefs inside the task description under a `## Triage Notes` heading, then replace the description:

```bash
dex edit "$ID" --description "$UPDATED_DESCRIPTION"
```

The triage skill's AI disclaimer must still be included at the top of each appended note:

```markdown
> *This was generated by AI during triage.*
```

Important: do **not** use `dex edit -n` for comments. In current dex, `-n` means `--name`, not “note”.

#### Close an issue

Use dex completion:

```bash
dex complete "$ID" --result "$RESULT" --no-commit
```

If implementation completed with a commit:

```bash
dex complete "$ID" --result "$RESULT" --commit "$SHA"
```

For `wontfix`, include the reason in `$RESULT`.


If implementing dex alongside Backlog.md later, include Backlog.md too. In this branch, keep the branch focused on dex.

### Explore step

Add dex detection hints:

```markdown
- `dex status`, `dex list --json`, or repo docs mentioning dex — sign dex may be the issue tracker
```

Do **not** default to dex just because the `dex` binary exists. dex can be installed globally while a repo uses another tracker. Prefer dex only if the repo already documents dex usage, dex has repo-local state, or the user says they use it.

### Section A choices

Add:



The triage-label docs can still use the word “roles”; for dex, the generated docs should explain that those roles map to `Triage-State` / `Triage-Type` fields in the task description.

### End-to-end smoke test in a scratch repo

Use a temporary repo, not this repo:

```bash
TMP=$(mktemp -d)
cd "$TMP"
git init
dex init
```

Then simulate the generated issue tracker doc commands:

```bash
PRD_BODY=$'Issue-Kind: prd\nTriage-State: needs-triage\nTriage-Type: enhancement\n\n## Problem Statement\nTest dex support.'
PRD_ID=$(dex create "PRD: Test dex support" --description "$PRD_BODY" --json | jq -r '.id')
TASK_BODY=$'Issue-Kind: issue\nTriage-State: needs-triage\nTriage-Type: enhancement\n\n## What to build\nSlice body.'
TASK_ID=$(dex create "Implement slice 1" --description "$TASK_BODY" --parent "$PRD_ID" --json | jq -r '.id')
dex show "$TASK_ID" --full
```

Then test triage metadata update manually:

```bash
UPDATED_BODY=$'Issue-Kind: issue\nTriage-State: ready-for-agent\nTriage-Type: enhancement\n\n## What to build\nSlice body.\n\n## Triage Notes\n\n> *This was generated by AI during triage.*\n\nAgent brief here.'
dex edit "$TASK_ID" --description "$UPDATED_BODY"
dex show "$TASK_ID" --full
dex complete "$TASK_ID" --result "Smoke test complete" --no-commit
```

Expected:

- PRD task is created
- child task is linked to parent
- metadata update preserves body content
- triage notes are visible in the description
- completion succeeds without a commit

## Acceptance criteria

- `/setup-matt-pocock-skills` offers dex as a first-class option.
- Setup writes a dex-specific `docs/agents/issue-tracker.md` from a seed template.
- `to-prd` has clear instructions for creating a PRD task.
- `to-issues` has clear instructions for child tasks and blockers.
- `triage` has clear instructions for metadata, notes, and completion.
- Existing GitHub, GitLab, and local markdown behavior remains unchanged.
- No old fork-only `task-backend` abstraction is reintroduced.

## Open questions

- Is description metadata good enough for dex triage, or should dex add native labels/status fields before this is first-class?
- Should `Triage-State` live at the top of the description or under a dedicated `## Metadata` heading?
- Should `to-prd` mark PRD tasks as `Triage-Type: enhancement`, or should PRDs use only `Issue-Kind: prd`?
- Should dex setup mention `dex sync` for users who later want GitHub/Shortcut synchronization, or would that confuse the core issue-tracker story?
